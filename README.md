# Syntara Monorepo

Monorepo combining the Syntara backend (Python/FastAPI) and frontend (React/TypeScript) into a single development and deployment environment.

## Repository Structure

```
syntara/
├── backend/          # Python 3.12+ / FastAPI API server, Temporal workflows
├── frontend/         # React 19 / TypeScript UI (npm workspaces)
├── Makefile          # Root orchestration (delegates to backend/ and frontend/)
├── podman-compose.yml # Full-stack local development
└── .env.example      # Combined environment variables
```

See [backend/README.md](backend/README.md) and [frontend/README.md](frontend/README.md) for component-specific documentation.

## Prerequisites

- **Python 3.12+** and [uv](https://docs.astral.sh/uv/) (backend)
- **Node.js 22+** and npm (frontend)
- **Podman** or Docker (container-based development)
- **Make** (orchestration)

## Quick Start

```bash
# One-time setup: install deps, generate secrets + TLS certs, build images, start services, migrate, seed
make setup

# Start full-stack development (backend API + frontend UI)
make dev

# Or use containers for the full stack
make -C backend run-all
```

## Plugin runtime-binding proof of concept

The `feature/plugin-runtime-bindings` branch extends the catalog-backed plugin flow with independent workload-image
options. A plugin release points to immutable plugin metadata (P); a separate RuntimeBinding (B) maps a plugin digest
and workload option to immutable image digests (I). Workflow authors can choose an installed option in the builder.
Syntara persists the selected binding and image digests with the workflow action. This is a proof of concept; it does
not provide production approval, rollback, retirement, or complete Execution Plane image dispatch.

```bash
mkdir syntara-marketplace
cd syntara-marketplace

git clone -b feature/plugin-runtime-bindings \
  git@github.com:ganeshrn/syntara.git syntara
git clone -b feature/runtime-release-bindings \
  git@github.com:syntara-orchestration/syntara-plugin-sdk.git syntara-plugin-sdk
git clone -b feature/plugin-platform-sdk-marketplace \
  git@github.com:ganeshrn/syntara-step-types.git syntara-step-types

# macOS only; safe to run when the machine is already running.
podman machine start

cd syntara/backend
make install
make build-images
make run-all
```

`make run-all` runs in the foreground. When the services are healthy, use the UI at
`http://localhost:8080` and the API readiness endpoint at `https://localhost:8000/healthz/ready`.

The backend consumes `syntara-plugin-contracts==0.1.0a3` from the configured Python package index. Release that prerelease
from the SDK branch before installing this Syntara branch; the dependency intentionally does not use a sibling checkout
or editable path.

Log in to the UI with the local administrator account. The bootstrap password is generated by
`make setup` (or `make secrets`) and stored only in `syntara/backend/.secrets/admin-password`.
Read it locally when needed:

```bash
cat backend/.secrets/admin-password
```

The `.secrets/` directory is git-ignored; do not commit or share the password. If you run the
backend bootstrap commands from `syntara/backend`, the same file is `.secrets/admin-password`.

The [Plugin SDK](https://github.com/syntara-orchestration/syntara-plugin-sdk/tree/feature/runtime-release-bindings)
provides the `syntara-plugin` authoring CLI and RuntimeBinding tooling. The
[reference plugin repository](https://github.com/ganeshrn/syntara-step-types/tree/feature/plugin-platform-sdk-marketplace)
contains the Local Echo and GitHub examples. Publish plugin and image digests, then refresh their respective indexes;
rebuilding Syntara is not part of plugin publication.

## Common Commands

| Command | Description |
|---|---|
| `make install` | Install backend and frontend dependencies |
| `make dev` | Start backend and frontend dev servers |
| `make test` | Run backend and frontend tests |
| `make test-all` | Run all tests including integration |
| `make lint` | Lint both codebases |
| `make format` | Format both codebases |
| `make typecheck` | Type-check both codebases |
| `make gen-contracts` | Regenerate TypeScript types from backend OpenAPI specs |

## Contract Generation

TypeScript API types are generated from the backend's OpenAPI specifications. In this monorepo, the specs are read directly from the local tree — no cross-repo cloning needed:

```bash
make gen-contracts
```

This reads specs from `backend/src/syntara/schemas/` and generates types in `frontend/packages/syntara-contracts/src/`.

## Container Development

The root `podman-compose.yml` provides the full stack: PostgreSQL, Redis, Temporal, the Syntara API, and the UI. The UI service builds from `frontend/` instead of pulling a pre-built image.

```bash
# Start all services
podman-compose up --build

# Start specific services
podman-compose up database redis temporal syntara
```

## Code Quality

Code quality and coverage are tracked via SonarCloud:

- **Backend**: [SonarCloud Dashboard](https://sonarcloud.io/project/overview?id=syntara-backend)
- **Frontend**: [SonarCloud Dashboard](https://sonarcloud.io/project/overview?id=syntara-frontend)

SonarCloud analysis runs automatically on all PRs. Quality gate results are **informational only**, pass/fail status is visible in the PR checks list but does not block merges. The required status checks for merge are `(Backend) Required Checks` and `(Frontend) Required Checks`, which cover linting, tests, type-checking, and builds.
